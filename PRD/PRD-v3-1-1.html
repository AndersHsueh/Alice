ALICE / VERONICA v3.1.1

A quiet expansion. Four P2 issues — observability, multi-agent collaboration, voice input, and a plugin marketplace — folded into one release. Twelve pull requests, five hundred and sixty-five new assertions, zero breaking changes to the public surface of v3.1.0.

01Executive summary

What this release is, and what it deliberately is not.

v3.1.0 closed the foundational arc — P1 × 9, the eight-item Zod v4 schema runtime, OpenTelemetry SDK scaffolding, the LSP integration, ripgrep substitution, the karpathy wiki ingest / lint bundled skills, and the token-budget bar. v3.1.1 opens the second arc: the long-promised P2 capabilities that sit on top of that foundation, with no rewrites underneath.

In one line

v3.1.1 makes ALICE an observable, collaborative, voiceable, and extensible assistant — without changing what v3.1.0 already shipped.

What is not in v3.1.1

  • No new runtime dependencies. All four P2 capabilities were built with the existing import surface. Voice, plugin sandboxing, marketplace signing, and multi-agent bus all use Node's built-in vm, crypto, child_process, and events modules.
  • No breaking API changes. Every P2 entry point is opt-in (a teamMessageBus? option, a voice_mode feature flag, a Marketplace class instantiated on demand, a PluginRegistry independent from the builtin tool list).
  • No remote infrastructure. The TeamMemorySync remote endpoint, real GPG / openpgp signature verification, real wake-word models (snowboy / openWakeWord), and the plugin marketplace HTTP API are all deliberately scoped out — v3.2.0 work.

02The four capabilities

Each capability is shipped as its own subsystem — independently testable, independently disable-able, independently replaceable.

I.

Observability · OTEL local dashboard

Built on top of v3.1.0's OpenTelemetry SDK (issue #11), the analytics layer reads the SDK's ~/.alice/otel/trace.jsonl console exporter output and surfaces a privacy-respecting local dashboard. The aggregator is a pure function — same input, same output, no IO, easy to test.

Privacy is enforced at the aggregator's exit. assertPrivacySafe walks the output object recursively and rejects any string value containing prompt, completion, system_prompt, user_message, or assistant_message substrings. The aggregator only ever emits counts and category names.

II.

Collaboration · multi-agent team

The original v3.0.1 Coordinator was a single-agent sequencer. v3.1.1 extends it into a true team: workers share a TeamMessageBus, can publish and acknowledge typed messages, and run with strict per-workspace locks so they don't trample each other's writes.

Five PRs build this in layers — protocol, tool binding, profile surface, runner integration, workspace coordination — each tested in isolation. The end-to-end contract is asserted in a single 24-assertion test that runs three workers concurrently against one bus.

III.

Input · voice

Four PRs land the voice subsystem as a clean abstraction: a VoiceProcessor base class with two implementations (NullVoiceProcessor for the default-off path, RealVoiceProcessor for the production stack), a WhisperCppEngine that spawns the whisper.cpp CLI as a child process, and a prototype EnergyWakeWordDetector keyed on RMS energy. The whole subsystem sits behind one feature flag: voice_mode.

The architectural contract is the single processUserInput(buffer) entry point. Whether the buffer is { kind: 'text', content } or { kind: 'voice', audio }, the function returns the same NormalizedInput shape. Downstream code does not need to know.

IV.

Extension · plugin marketplace

Four new source files plus tests give ALICE a real plugin surface. A PluginManifest is validated with a Zod v4 schema; a PluginRegistry holds installed plugin info; a PluginSandbox runs plugin code in a vm context with a whitelist for require and process.env; a Marketplace wraps the install path with HMAC-SHA256 signature verification.

The end-to-end fixture — loadPluginSampleWeather() — signs a manifest, installs it, loads the tool into the host registry, invokes get_weather('北京'), and asserts the round-trip result. 39 assertions cover the entire chain.

Layering

The four new capabilities share one architectural decision: they all sit above v3.1.0, not inside it. None of the P2 changes touched:

  • The agent loop core (src/runtime/agent/agentLoop.ts)
  • The permission system (src/core/permission/*)
  • The build-time DCE pipeline (src/runtime/feature/buildTimeDCE.ts)
  • Any tool in src/tools/builtin/ except the new teamMessage.ts

This is what makes the test count 1173 instead of something much higher — the new code is self-contained and tests don't have to mock the existing surface.

05Migration & compatibility

v3.1.1 is a strict additive release. Every v3.1.0 consumer should upgrade without code changes.

Upgrade

No new dependencies, no breaking API changes, no database migrations. The release commit is on main at b71ed55, tagged v3.1.1.

Behavior changes you may notice

  • Profile list now shows 4 spawnable. The :agents slash command will list consultant, researcher, executor, and reviewer instead of just two. If you have UI that enumerates the set, expect the count to grow.
  • Run-loop is no-op compatible. If you don't pass teamMessageBus to runAgents(), the behavior is byte-identical to v3.1.0.
  • Voice is opt-in by flag. Until a user adds voice_mode: true to ~/.alice/settings.jsonc, no voice code runs at all (NullVoiceProcessor).
  • Plugin system is inert without an explicit Marketplace. The PluginRegistry, PluginSandbox, and Marketplace classes are not imported by any existing call site. Nothing executes until you instantiate one.

08Roadmap to v3.2.0

The next batch is bounded by what v3.1.1 explicitly leaves undone.

Concretely, the v3.2.0 candidate list

  1. Streaming OTEL dashboard. Watch trace.jsonl via fs.watch, render deltas instead of re-reading the whole file.
  2. Real wake-word model. Swap EnergyWakeWordDetector for a SnowboyWakeWordDetector / OpenWakeWordDetector that loads a model file. The WakeWordDetector interface does not need to change.
  3. Real GPG signature verification. Replace the HMAC layer with openpgp or a gpg subprocess. verifySignature signature stays the same; the implementation underneath swaps.
  4. Plugin marketplace HTTP API. A new MarketplaceClient class that fetches a manifest from a URL, verifies its signature against a pinned public key, and runs the existing Marketplace.install path.
  5. Cross-OS audio capture. AVFoundationCapture (macOS), WASAPICapture (Windows), PulseAudioCapture (Linux). The AudioCapture interface from v3.1.1 is what they implement.
  6. Profile #3 — writer. Use the same LLM-planner shape as executor, tuned for prose rather than code steps.

None of these change the v3.1.1 surface. They extend it.

09Closing note

For the next person who has to maintain this.

v3.1.1 is intentionally small. It is four features, each one shipped behind its own flag, each one independently testable, each one with a known placeholder for the next thing. The codebase grew by roughly 15 source files and 4,000 lines of test code; nothing else moved.

If you are debugging one of these subsystems, the fastest path is: test-list.md → the matching test-issue-NNN.ts → run it under bun. The tests are not unit tests with mocks; they construct real TeamMessageBuses, real vm sandboxes, real child_processes for whisper.cpp stubs, and real fs writes for the registry scan. The behavior is the behavior.

If you are extending one of these subsystems: the interfaces (VoiceProcessor, PluginLoader, Marketplace, WorkspaceCoordinator) are small on purpose. Read the file, not the docs.

The rule of thumb

Ship the smallest honest thing. Then the next smallest honest thing. Then stop.
