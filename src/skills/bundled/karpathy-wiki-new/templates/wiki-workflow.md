# Wiki 工作流:Ingest / Query / Lint

> 最后更新:2026-08-09

## 摘要

本页把 Karpathy LLM Wiki 模式的三类核心操作(**Ingest / Query / Lint**)固化成可执行 checklist:每类操作写清触发条件、逐步动作、必登的 log 条目、以及失败时怎么办。Ingest 与 Lint 各有对应技能(`/karpathy-wiki-ingest`、`/karpathy-wiki-lint`),Query 直接在库目录里提问即可;不用技能、手工推进时也照本页执行。触发发生时不可跳步 —— 跳掉的每一步,最后都会变成断链、孤岛页或者一句查无出处的结论。

## 一、Ingest 工作流(新源摄取)

### 触发条件

- 用户往 `raw/` 放了**任何**新文件(`.md` / `.txt` / `.pdf` / `.docx` / `.xlsx` / 图片 / 网页剪藏等)
- 用户说「消化一下这份资料」「把这个录进 wiki」「raw 入仓」
- 用户在对话里直接粘了一大段材料(文章、记录、摘录)—— 本质等同 ingest,先落 `raw/` 再走流程

### 开工前:选节奏(待编译的源多于 1 份时)

先问用户一句「**逐份确认(推荐)还是批量一次跑完?**」,Karpathy 原文的首选做法是人在环路里:*"Personally I prefer to ingest sources one at a time and stay involved."*

| 模式 | 怎么做 |
|------|--------|
| **逐份**(推荐) | 每份源在**写页面之前**,先输出 3-5 句 key takeaways + 计划触及的页面清单,等用户点头或补一句「重点看什么」,再走下面的 Checklist 落盘 |
| **批量** | 按下面的 Checklist 逐份跑完,最后一次性汇报改了哪些页 |

用户选完就把这个偏好写进 [[../CLAUDE.md]] 的「⚙️ 操作中要注意」,之后照此执行,不必每次重问。

### Checklist(按顺序执行)

- [ ] **Step 1:归纳源类型**
  - **从内容本身归纳类别,不要套死枚举**。跨领域参考:文章 / 论文 / 书籍章节 / 访谈或对话记录 / 会议记录 / 个人笔记 / 数据表 / 图片 / 网页剪藏 / 其它
  - 若这个库已经形成了自己的类别习惯,沿用既有类别,不要每次发明新词
  - 实在判断不了 → 停下来问用户一句,不猜
  - 素材含内联图片时:**先读文本,再按需单独打开图片**(带图 markdown 无法一次读全)

- [ ] **Step 2:登记到 log.md**
  - 追加一条 `## [YYYY-MM-DD] ingest | <源文件简述>`
  - 必含:源文件路径、源类型、3-5 句内容摘要、这份源带来的关键结论或分歧点(如有)

- [ ] **Step 3:决定影响范围**
  - 先问自己:这份源会触及哪些主题?一份稍有分量的源,常常同时影响多个页面
  - 决策树:
    - 出现了新概念 / 新实体 / 新专题 → **新建** wiki 主题页
    - 已有主题的补充、修订、反例 → **更新**对应主题页
    - 只是佐证已有结论,没有新信息 → 在 `INDEX.md` 的来源清单登记即可
    - 引出了没人能回答的问题 → 新建 `待澄清-<主题>.md`,写清问题、已知线索、需要谁拍板

- [ ] **Step 4:执行 wiki 变更**
  - 新建主题页:必备 `## 摘要` + 日期戳 `> 最后更新:YYYY-MM-DD` + 建议互链到至少 3 个相关主题(格式见 [[../CLAUDE.md]] 的结构纪律)
  - 更新主题页:**直接改写正文与 `## 摘要`**,让这一页反映当前最优综述 —— Karpathy 原文的 ingest 就是 *"revising topic summaries"*,不是把每一版结论都摞上去;被推翻的旧说法值得留痕的压成 `## 修订记录` 一行,不值得的交给 git;同步更新该页日期戳(确实需要显式留痕时才加 `> 已过时:` 注记,四个标记的用法见 [[../CLAUDE.md]] 的注记标记表)
  - 更新 `INDEX.md`:新主题进主题清单、新源进来源清单、关键事实速查表同步
  - 引用要落到具体位置(文件 + 章节 / 页码 / 行号区间),便于日后回溯

- [ ] **Step 5:登记 wiki 变更到 log.md**
  - 追加一条 `## [YYYY-MM-DD] wiki | <变动摘要>`,列出新增和被改的文件名

- [ ] **Step 6:自检(与 lint 同口径的 5 项)**
  1. 新增 / 修改的页面都有 `## 摘要`
  2. 都有当天的日期戳
  3. 每个新主题页的出链数建议 ≥ `MIN_LINKS`(默认 3;不足只是提示,不算不达标 —— 不要为了凑数去链无关页面或造断链)
  4. 页内引用的 `[[目标]]` 都真实存在(跨域的 `raw/`、`outputs/`、`../CLAUDE.md` 除外)
  5. 新页至少被 `INDEX.md` 或某个主题页链到,不是孤岛
  - 另外确认:`raw/` 里的源文件**一个字都没改**;`log.md` 末尾新增了 ingest 与 wiki 两类条目

### 失败处理

| 情况 | 处理 |
|------|------|
| 源类型判断不了 | 停下问用户,不猜测 |
| 找不到合适的主题归属 | 新建一页,不要硬塞进不相关主题 |
| 源本身有错(错别字 / 自相矛盾) | **不改 raw**,在对应主题页加注 `> 待澄清:YYYY-MM-DD raw/X 某处有 Y 问题`(标记用法见 [[../CLAUDE.md]] 的注记标记表) |
| 一份源触及的页面太多、一次做不完 | 先建页面骨架(摘要 + 戳 + 互链)并登 `todo` 条目,下次续 |
| 源与已有 wiki 结论冲突 | 新源证据更强就直接改写主题页;一时判不出谁对,两边都加 `> 矛盾:` 注记,进入 lint 的矛盾流程,别自己拍板选一个 |

## 二、Query 工作流(查询 + 回填)

> Query 没有单独的技能:你在知识库目录里直接提问即可,`CLAUDE.md` 会把本节作为工作流加载。

### 触发条件

- 用户就库内内容提问("X 是什么""这个结论的依据是哪份源")
- 用户要求对比、汇总、分析、推导("X 和 Y 有什么差别""把所有主题的状态汇总一下")
- 用户要一份产物(报告、对比表、幻灯片、图表)

### Checklist

- [ ] **Step 1:决定查询模式**

  | 模式 | 判断依据 | 读什么 |
  |------|----------|--------|
  | 简单事实 | 答案落在单个主题页内 | `INDEX.md` → 1 个主题页 |
  | 跨主题综合 | 需要拼接多个主题 | `INDEX.md` → 相关的 2-4 个主题页 |
  | 探索性研究 | 问「为什么」「怎么演变的」「有没有遗漏」 | `INDEX.md` → grep `log.md` 看时间线 → 多个主题页 → 必要时回 `raw/` |

- [ ] **Step 2:定位与阅读**
  - 小规模默认先读 `INDEX.md` 定位,不要一上来就 grep 全库
  - **规模出口**:主题页超过 150 页,或 `INDEX.md` 自己长到读一遍就吃掉大半上下文时,改用检索工具先捞候选页,**再回 `INDEX.md` 校对归属**。工具选型:qmd(BM25 + 向量混合检索、LLM 重排,CLI 与 MCP 两种接法)/ `rg -l "<关键词>" wiki/` / 让 LLM 现搓一个朴素搜索脚本
  - 再读相关主题页;需要时间线或决策沿革时 `grep "^## \[" wiki/log.md`
  - 页面里引用了图片,先读文本,再按需单独打开那张图
  - 主题页说不清、需要原始表述时,才回 `raw/` 读原文

- [ ] **Step 3:带引用回答**
  - 每个事实都标注出处:来自**哪个 wiki 页** + 背后的**哪份 raw 源**
  - **禁止用训练数据补库内特定事实**。库里没有就直说没有,并给出补法(先 ingest 哪份材料)
  - 库内两处说法冲突 → 两处都摆出来,标明冲突,不要替用户选一个
  - 推断出来的结论要明确标成推断,和有源可查的事实分开写

- [ ] **Step 4:回填决策**
  - **回填阈值:任何「下次还会用到」的答案,都值得回填。** 一次性事实不回填
  - 决策矩阵:

    | 答案类型 | 是否回填 | 落点 |
    |----------|----------|------|
    | 一次性事实查询("这个数是多少") | ❌ 不回填 | —— |
    | 跨主题对比 / 综合分析,结论有沉淀价值 | ✅ 回填 | 新建 `对比-<A>-与-<B>.md` 或 `汇总-<维度>.md` |
    | "为什么是这样"的推理链,补上了 wiki 没显式写出的逻辑 | ✅ 回填 | 在最相关主题页追加 `## 推理与依据` 段 |
    | 现状评估 / 阶段盘点 | ✅ 回填 | 新建 `盘点-<YYYY-MM-DD>-<主题>.md` |
    | 发现了库里的空白或矛盾 | ✅ 回填 | 新建 `待澄清-<主题>.md`,并登 `todo` |
    | 需要给别人看的成品 | ✅ 产出 | 写进 `outputs/`,并登 `deliverable` |

- [ ] **Step 5:执行回填**
  - 新建页面:`## 摘要` + `> 最后更新:YYYY-MM-DD` + 建议互链到至少 3 个相关主题;回填页命名一律取自 [[../CLAUDE.md]] 的命名约束,不要自造新前缀
  - 追加段落:在原页面加新段(推理链固定落 `## 推理与依据`)+ 更新该页日期戳
  - **撞上旧结论时直接改写,不要堆叠**:新结论推翻了页面上的旧说法,就重写正文与 `## 摘要`,让这一页保持一份当前最优综述;旧说法值得留痕的压成 `## 修订记录` 一行,或者交给 git。整个库里只有 `log.md` 是 append-only
  - 更新 `INDEX.md`:新主题进清单,必要时更新关联图与关键事实速查
  - 追加 `## [YYYY-MM-DD] query | <问题 + 回填去向>` 到 `log.md`
  - 若同时产出了 `outputs/` 里的东西,再追加一条 `## [YYYY-MM-DD] deliverable | <产物简述>`

- [ ] **Step 6:自检**
  1. 回答里每个事实点都能指到具体的 wiki 页或 raw 源
  2. 回填的新页面有摘要、日期戳,出链建议 ≥ `MIN_LINKS`(默认 3;不足只提示,不算不达标)
  3. `INDEX.md` 已同步(如有新页)
  4. `log.md` 已登 `query` 条目(如有产物,还有 `deliverable`)

### 输出形态

回答不一定只是聊天里的一段话。按用户需要选形态,成品一律落 `outputs/`:

- **markdown 报告** —— 最常用,可直接进 `outputs/`
- **对比表** —— 多对象多维度比较,markdown 表格或 CSV
- **Marp 幻灯片** —— 需要讲给别人听时
- **matplotlib 图表** —— 有数值趋势、分布、时间线时
- **数据文件** —— CSV / JSON,给下游工具用
- **canvas / 关系图** —— 主题之间的关联结构

### 反模式(禁止)

- ❌ 用训练数据硬补库内特定事实
- ❌ 答案很有价值却不回填 —— 散在对话历史里,下次还得重新推导一遍
- ❌ 回填时漏写摘要、日期戳
- ❌ 为了凑够出链数去链无关页面,或链到还不存在的页面制造断链
- ❌ 回填了新页却不更新 `INDEX.md`,制造孤岛
- ❌ 小规模库里跳过 `INDEX.md` 直接全库 grep,读一堆无关内容(超规模改走检索是另一回事,见 Step 2)
- ❌ 回填页自造命名前缀,或把推理链塞进随手起的段名

## 三、Lint 工作流(健康检查)

### 触发条件

- **例行**:每周一次(建议一周收尾时跑)
- **节点触发**:每次较大规模 ingest 之后 / `INDEX.md` 结构调整之后 / 生成正式产物之前
- **被动触发**:发现某个 `[[链接]]` 点不开,或某页内容明显过时

### 3.0 先跑脚本,再动手

不要手写一次性的检查脚本 —— `/karpathy-wiki-lint` 技能自带 `lint-scripts.sh`,断链、orphan、摘要、日期戳、链接密度五项一次跑完。

```bash
# 定位技能自带的脚本。优先级:用户级手装 → 插件安装 → 项目本地。
# 插件层用 find 而不是通配符:插件真实落盘深度不固定,且 zsh 默认 nomatch
# 会让未匹配的通配符直接报错中止整段(bash 才是保留字面串)。零 glob = 零方言问题。
LINT_SH="$HOME/.claude/skills/karpathy-wiki-lint/references/lint-scripts.sh"
[ -f "$LINT_SH" ] || LINT_SH=$(find "$HOME/.claude/plugins" -name lint-scripts.sh -path '*karpathy-wiki-lint*' -print -quit 2>/dev/null)
[ -f "$LINT_SH" ] || LINT_SH="./.claude/skills/karpathy-wiki-lint/references/lint-scripts.sh"
[ -f "$LINT_SH" ] || { echo "❌ 找不到 lint 脚本,技能安装不完整"; exit 1; }

# 在知识库根目录或 wiki/ 目录内运行,结果完全一致
bash "$LINT_SH"

# 想临时提高链接密度要求时,用环境变量覆盖(默认 MIN_LINKS=3)
MIN_LINKS=4 bash "$LINT_SH"
```

脚本行为约定:

- **调用位置无关** —— 从知识库根(含 `wiki/` 子目录)或从 `wiki/` 目录内运行,输出一致
- **正常运行 stderr 为空,退出码 0** —— 即使查出问题也返回 0,问题都在 stdout 里
- 日期戳识别**与年份无关**,任何 `YYYY-MM-DD` 格式的真实日期都算有效戳;`> 最后更新:` 与 `> Last updated:` 两种写法等价,除此之外没有第二种写法算有戳
- 目标里含 `/` 的**跨域引用一律跳过**(`raw/...`、`outputs/...`、`../CLAUDE.md`),不算断链
- fenced code block 内和行内反引号里的示例链接一律跳过

输出格式:

```text
BROKEN: <链接目标> (referenced by: a.md, b.md)
ORPHAN: <文件名>
NOSUMMARY: <文件名>
NOSTAMP: <文件名>
LOWLINKS: <文件名> (n < MIN_LINKS)
SUMMARY: broken=0 orphans=0 lowlinks=0 nosummary=0 nostamp=0
```

最后一行 `SUMMARY:` 是机器可读汇总。`broken` / `orphans` / `nosummary` / `nostamp` 四项归零才算体检通过;`lowlinks` 只是**提示(INFO)**,脚本负责测量、不负责判分 —— 主题页总数少于 8 的小库直接忽略它。

### 3.1 断链检查

对脚本报出的每条 `BROKEN:`(`referenced by` 已经告诉你是谁在引用它)做决策:

| 断链目标的性质 | 处理 |
|----------------|------|
| 是真实存在的概念,只是还没写页 | **新建主题页**(摘要 + 日期戳 + 出链建议 ≥ `MIN_LINKS`),然后进 `INDEX.md` |
| 是错别字或旧页名 | 改引用方的链接,不必新建页 |
| 是本来就该拆出来的子主题 | 从来源页拆分内容成新页,双向互链 |
| 是已被合并掉的旧主题 | 把引用改指向合并后的页面 |

修完追加一条 `## [YYYY-MM-DD] lint | 修复 N 条断链` 到 `log.md`。

### 3.2 Orphan 检查

Orphan = 没有任何其它页面链向它。`INDEX.md`、`log.md` 和本工作流页不参与这项检查(它们本来就是入口或元文档)。

| Orphan 的性质 | 处理 |
|---------------|------|
| 确实该被链接的主题 | 在 [[INDEX]] 的主题清单里显式列入,并在最相关的主题页加一条互链 |
| 内容还没长成,只是草稿 | 顶部标注 `> 草稿:待整合`,写明打算并进哪一页,并登一条 `todo` |
| 看起来已经废弃 | **只建议,不自动删除** —— 把候选列成清单交给用户,说明理由;用户明确说删才删 |

> ⚠️ LLM 永远不主动删除 wiki 页面。删除是不可逆动作,必须由用户明确指令触发。

### 3.3 矛盾检查

脚本查不出语义矛盾,这一项要靠阅读。按这些通用维度扫:

| 维度 | 典型矛盾 |
|------|----------|
| 日期与时间线 | 同一件事在两页写了不同时间,或先后顺序对不上 |
| 数值与统计量 | 同一指标两页数字不同,或口径不一致却直接比较 |
| 术语与定义 | 同一个词在不同页指不同东西,或同一概念用了两个名字 |
| 实体属性 | 同一对象的归属、角色、分类前后不一致 |
| 状态与结论 | 一页说已确定,另一页仍写作待定 |
| 版本与修订 | 引用了不同版次的材料却当成同一份 |

能当场判出谁对的(比如一页明显基于更新的源),**直接改写落后的那一页**,不要两边都挂着注记等人来收。判不出的,在**所有**冲突页面都加一条注记,并同步更新这些页的日期戳:

```text
> 矛盾:YYYY-MM-DD 此页与 [[另一主题#某小节]] 关于「某指标」的说法不一致,待澄清
```

一次会话内解决不了的,单开一页 `待澄清-<主题>.md` 汇总,并登 `todo` 条目。

> 四个注记标记(`> 已过时:` / `> 矛盾:` / `> 待澄清:` / `> 草稿:`)的适用场景以 [[../CLAUDE.md]] 的**注记标记表**为唯一定义,不要自创写法。

### 3.4 摘要 / 日期戳 / 链接密度

脚本已覆盖这三项,规则是:

- 每页必须有 `## 摘要`(对应 `NOSUMMARY:`)—— 硬项,必须修;英文库写 `## Summary` 同样算
- 每页必须在摘要上方有 `> 最后更新:YYYY-MM-DD`(对应 `NOSTAMP:`)—— 硬项,必须修;英文库写 `> Last updated:` 同样算
- 除 `INDEX.md` / `log.md` / 本工作流页外,建议每页的 `[[]]` 出链不低于 `MIN_LINKS` 条(默认 3,对应 `LOWLINKS:`)—— **提示项**,不是不达标

`LOWLINKS:` 怎么处理:先看这一页是不是真的孤零零 —— 是就顺手补几条**真实**互链;只是这个主题天然没什么邻居,就放着不管。**绝不允许为了把 `lowlinks` 压到 0 去链无关页面,或者链到还不存在的页面制造断链** —— 那是拿真断链换假达标。

补戳时用**当天真实日期**,不要为了让检查通过而随手编一个;戳代表这一页最后一次被核对的时间。

### 3.5 修复后收尾

- [ ] 重跑一次脚本,确认 `broken` / `orphans` / `nosummary` / `nostamp` 四项归零(`lowlinks` 是提示项,残留可以接受,但要在收尾里说清哪几页、为什么留着)
- [ ] 被改动的页面日期戳已更新
- [ ] `INDEX.md` 与实际页面清单一致
- [ ] 追加 `## [YYYY-MM-DD] lint | <修了什么、还剩什么>` 到 `log.md`
- [ ] 用了 git 的库,顺手 `git commit -m "lint: <修了什么>"` 存一个可回溯的检查点

### 失败处理

| 情况 | 处理 |
|------|------|
| 矛盾一次会话内解决不了 | 建 `待澄清-<主题>.md` 汇总,登 `todo`,留给用户拍板 |
| orphan 超过 5 个 | 暂停新建页面,先把现有结构接起来 |
| 断链集中在同一主题 | 这个主题多半该拆分,或者它引用的子概念一直没落地 |
| 找不到 `lint-scripts.sh` | 说明技能安装不完整;先重装技能,再用 §六 的手工命令临时顶一下 |

## 四、维护节奏

| 操作 | 触发频率 | 建议时机 |
|------|----------|----------|
| Ingest | 每次 raw 入仓 | 即时,不拖到下次会话 |
| Query | 每次提问 | 即时,回填判断跟着答案一起做 |
| Lint | 每周 + 关键节点 | 一周收尾时 + `INDEX.md` 调整后 + 出正式产物前 |

## 五、与其他文件的关系

- [[INDEX]] —— 内容导向的目录。任何页面增删改名、任何 lint 修复之后,都要回来同步主题清单与关键事实速查
- [[log.md]] —— 时间导向、append-only 的流水。三类操作的每一次都必登此处,类型只能取 `{ingest, query, wiki, lint, deliverable, milestone, todo}`
- [[../CLAUDE.md]] —— 知识库的 schema,其中「维基规则」是本工作流的强约束来源(结构纪律 / 时间戳纪律 / 维护纪律)。三样东西以它为**唯一定义**,本页只引用不复述:**注记标记表**(四个标记的适用场景)、**命名约束**(回填页取名)、**版本历史交给 git**(重写正文的兜底)。它与用户共同演化:发现更顺手的工作流约定时,主动提议修改,经用户确认后再改,并在 log 登一条 `wiki` 条目
- `待澄清-<主题>.md` —— 矛盾与开放问题的归口。lint 里解决不了的、ingest 中冒出来没人能答的,都汇到这类页面
- **git**(可选但强烈建议)—— 知识库就是一个 markdown git 仓库,版本历史白送。每次 ingest / query 回填 / lint 修复之后 commit 一次;正因为有它兜底,主题页才敢直接重写,而不必把历次结论堆在页尾

## 六、手工速查命令

脚本不可用时的临时替代,或者只想快速瞄一眼时用。**在知识库根目录执行**。

```bash
# 1) 每页的 摘要 / 日期戳 / 出链数 一览(日期戳判定与年份无关)
#    中英两套写法等价,与 lint 脚本默认口径一致;
#    注意冒号用分组交替 (：|:) 而非字符组 [：:] —— LC_ALL=C 下全角冒号会被按单字节拆开。
for f in wiki/*.md; do
  s=$(grep -cE '^## (摘要|Summary)' "$f")
  d=$(grep -cE '(最后更新|Last updated)(：|:)[[:space:]]*[0-9]{4}-[0-9]{2}-[0-9]{2}' "$f")
  l=$(grep -oE '\[\[[^]]+\]\]' "$f" | wc -l | tr -d ' ')
  printf '%s | 摘要:%s | 戳:%s | 出链:%s\n' "$(basename "$f")" "$s" "$d" "$l"
done

# 2) 最近 5 条 log
grep '^## \[' wiki/log.md | tail -5

# 3) 按类型过滤 log
grep -E '^## \[[0-9]{4}-[0-9]{2}-[0-9]{2}\] (ingest|query|wiki|lint|deliverable|milestone|todo) \|' wiki/log.md

# 4) 三层各有多少东西
printf 'raw: %s\n'     "$(find raw     -type f ! -name 'README.md' 2>/dev/null | wc -l | tr -d ' ')"
printf 'wiki: %s\n'    "$(find wiki    -type f -name '*.md'        2>/dev/null | wc -l | tr -d ' ')"
printf 'outputs: %s\n' "$(find outputs -type f ! -name 'README.md' 2>/dev/null | wc -l | tr -d ' ')"
```

> 断链与 orphan 不要手写脚本临时凑 —— 边界情况(代码块、行内反引号、别名、锚点、跨域引用、文件名里的括号)太多,一律交给 `lint-scripts.sh`。
