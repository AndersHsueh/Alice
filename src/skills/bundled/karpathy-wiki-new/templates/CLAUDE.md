## 📁 目录结构

| 目录 | 归属 | 规则 |
|------|------|------|
| `raw/` | 用户 | 原始素材。**LLM 只读,禁止修改**(哪怕发现错别字) |
| `wiki/` | LLM | LLM 完全拥有并维护的 markdown 网络,每主题一页,互相链接 |
| `outputs/` | LLM | 对外产出:markdown 报告 / 对比表 / Marp 幻灯片 / 图表 / 数据文件 / 图片 |

## 📐 维基规则

> 本节是 LLM 维护 wiki 的强约束。每一条都不可绕过。

### 结构纪律

- **每主题一文件** —— 每个独立主题一个 `.md` 文件,文件名用中文短语(避免空格;英文名仅限约定俗成者)
- **每页摘要** —— 每个 wiki 页面开头必须有 `## 摘要` 段落,用 3-5 句浓缩这一页讲什么。**中英两套等价**:`## 摘要` 与 `## Summary`,lint 默认都认(整库统一用一种即可)
- **互链格式** —— 用 `[[主题名]]` 互相链接,可带节锚 `[[主题名#子标题]]`,可带别名 `[[主题名|显示文字]]`
- **链接密度(建议项)** —— 除 `INDEX.md` / `log.md` / 工作流页外,建议每个主题页至少 3 条出链(阈值即 lint 的 `MIN_LINKS`,默认 3);不足只是提示这一页还没接进知识网络,不要为了凑数去链无关页面,更不要制造指向不存在页面的断链。**主题页总数不足 8 页的小库,这一项一律忽略** —— 页少的时候链不满是物理事实,不是质量问题
- **跨域引用** —— 指向 `raw/`、`outputs/`、`../CLAUDE.md` 的链接照写,它们不算断链
- **索引维护** —— 新增 / 重命名 / 删除 wiki 页面后,必须同步更新 `wiki/INDEX.md`(主题清单 + 关联图 + 关键事实速查)

### 时间戳纪律(强制)

- **每页必须有日期戳** —— 在 `## 摘要` 上方写一行 `> 最后更新:YYYY-MM-DD`,这是该页内容时效性的真实声明。**中英两套等价**:`> 最后更新:` 与 `> Last updated:`,lint 默认都认;除这两种写法之外没有第二种算有戳
- **更新即改戳** —— 任何内容变更(修订事实、新增段落、纠正错误)都要同步更新该页日期戳
- **主题页是当前最优综述,可以放心重写** —— 发现事实已变,**优先直接改写正文与 `## 摘要`**,让这一页反映当下最好的理解。Karpathy 原文的 ingest 就是 *"**revising** topic summaries"*,要的是一份现在就能用的综述,不是历次结论的地层。被推翻的旧说法值得留痕的,压缩成 `## 修订记录` 里的一行;不值得的,直接交给 git(`git log -p wiki/<页面>.md` 就能找回旧说法)
- **只有 `wiki/log.md` 是 append-only** —— log 只追加不改写;主题页不受这条约束

#### 注记标记表(全库唯一定义)

需要在页面上留一条显式注记时,只用下面这四个标记,不要自创写法。工作流页与各技能一律引用本表。

| 标记 | 适用场景 |
|------|----------|
| `> 已过时:YYYY-MM-DD ...` | 本页**事实已被更新的源推翻**。优先直接改写正文,只有需要留痕时才加这条注记,并指向新的依据 |
| `> 矛盾:YYYY-MM-DD 此页与 [[X]] 不一致,待澄清` | 与另一页冲突、本会话内无法裁决 —— 所有冲突页都要加,并同步改戳 |
| `> 待澄清:YYYY-MM-DD ...` | **源本身**有问题(错别字 / 自相矛盾 / 信息不足),或需要人来拍板 |
| `> 草稿:待整合` | 临时页,还没并入主题网络;写明打算并进哪一页,并登一条 `todo` |

### 维护纪律(强制)

- **新源入仓 → 同一次会话内闭环** —— 每往 `raw/` 落一份新文件,必须:
  1. 在 `wiki/log.md` 追加一条 `## [YYYY-MM-DD] ingest | <源文件简述>`
  2. 同步更新受影响的 wiki 主题页(引用该源、提取关键事实),或在 `INDEX.md` 的来源清单登记
  3. 必要时新增 / 重命名 wiki 主题页
- **任何 wiki 变更 → log 必登** —— 新增、重写、纠正过时事实,追加 `## [YYYY-MM-DD] wiki | <变动摘要>`
- **查询回填 → log 必登** —— 把一次问答的结论沉淀成页面或段落时,追加 `## [YYYY-MM-DD] query | <问题与回填去向>`
- **阶段性节点 → log 必登** —— 一个研究阶段收尾、一本书读完一部分、一次复盘完成,追加 `## [YYYY-MM-DD] milestone | <节点简述>`
- **产出物 → log 必登** —— `outputs/` 下生成任何正式产物时,追加 `## [YYYY-MM-DD] deliverable | <产物简述>`
- **体检修复 → log 必登** —— 每次跑完 lint 并修复问题,追加 `## [YYYY-MM-DD] lint | <修了什么>`
- **悬而未决 → log 必登** —— 需要用户拍板或后续补充的事,追加 `## [YYYY-MM-DD] todo | <待办>`
- **log.md 类型集** —— `{ingest, query, wiki, lint, deliverable, milestone, todo}`,不要自创类型
- **grep 友好** —— log 条目格式固定为 `## [YYYY-MM-DD] type | title`,可被 `grep "^## \[" wiki/log.md` 直接解析
- **append-only(全库仅此一处)** —— `log.md` 只追加不改写;写错了就再补一条修正条目。主题页不适用这条,它们该改就改

### 三类操作工作流

Karpathy 模式的三大操作,每一类都有对应技能和可执行 checklist:

| 操作 | 技能 | 一句话 |
|------|------|--------|
| **Ingest** | `/karpathy-wiki-ingest` | 新源入仓 → log 登记 → 影响范围决策 → wiki 变更 → log wiki 条目 → 自检 |
| **Query** | 直接提问(见工作流页 §二) | 提问 → 定位与阅读 → **带引用回答** → 回填决策 → 执行回填 → 自检 |
| **Lint** | `/karpathy-wiki-lint` | 周期体检:断链 / orphan / 矛盾 / 摘要戳与链接密度 → 修复 → log lint 条目 |

三类操作的完整 checklist 见 [[工作流-ingest-query-lint]](§一 Ingest / §二 Query / §三 Lint)。

> **Query 的复利机制**:好答案要回填成新页面。Karpathy 原文 —— *"good answers can be filed back into the wiki as new pages... your explorations compound in the knowledge base just like ingested sources do."*

> **图片两段式读取**:带内联图的 markdown 无法一次读全。先读文本,再按需单独打开被引用的图片。

### 命名约束

- 文件名优先用中文短语,见名知意(如 `研究方法.md`、`第三章-核心论点.md`)
- 避免英文文件名,除非约定俗成(`INDEX.md`、`README.md`、`CLAUDE.md`)
- 时间型主题:`<事件类型>-<MMDD>.md`(如 `读书笔记-0612.md`)
- 开放问题 / 尚未有定论的事:`待澄清-<主题>.md`,在页内列出问题、已知线索、需要谁来拍板
- 阶段性盘点 / 现状评估:`盘点-<YYYY-MM-DD>-<主题>.md`
- 多对象横向比较:`对比-<A>-与-<B>.md`
- 按某个维度横切汇总:`汇总-<维度>.md`
- 查询回填的推理链不单独开页,追加到最相关主题页的 `## 推理与依据` 段
- 以上前缀是全库统一的登记表 —— 回填页一律从这里取名,不要自造新前缀

### 不可触碰

- `raw/` 下任何文件**禁止修改** —— 即便发现错别字、格式问题、事实错误,也只能在对应 wiki 主题页注明「原 `raw/X` 某处有 Y 问题」,绝不动源文件

## ⚙️ 操作中要注意

这里写本知识库特定的环境 / 工具 / 协作约束。下面三条是默认就写好的工作流偏好,其余按你的场景增删。

- **本库的书写语言** —— 默认中文。lint 的摘要标题与日期戳**中英两套都认**(`## 摘要` / `## Summary`、`> 最后更新:` / `> Last updated:`),整库统一用一种即可。若本库换了别的措辞(例如摘要小节叫 `## 概要`),把口径记在这一条后面,并让 LLM 按 schema 演化流程同步改 lint 脚本里的常量 —— 否则会满库误报 NOSUMMARY / NOSTAMP。

- **Ingest 节奏偏好** —— 待编译的源多于 1 份时,LLM 先问一句「逐份确认(推荐)还是批量一次跑完?」。**逐份**= 每份源在落盘之前先给 3-5 句 key takeaways + 计划触及的页面清单,等你点头或补一句「重点看什么」再写;**批量**= 一次跑完再汇总汇报。你的选择由 LLM 追写在这一条后面,之后照此执行、不再每次重问;改主意了直接改这一行。
- **规模出口:库大了就上检索** —— Karpathy 原文:*"at small scale the index file is enough, but as the wiki grows you want proper search"*。小规模默认先读 `wiki/INDEX.md` 定位;等主题页涨到 150 页以上、或 `INDEX.md` 自己长到读一遍就吃掉大半上下文,改用检索工具先捞候选页,**再回 `INDEX.md` 校对归属**。
  - **qmd**(原文点名):本地 markdown 混合检索,BM25 + 向量召回再叠一层 LLM 重排,**CLI 与 MCP 两种接法**都有 —— CLI 适合在会话里直接跑一条命令拿候选页,MCP 适合挂成工具让模型自己按需检索
  - 关键词很明确时,`rg -l "<关键词>" wiki/` 就够
  - 不想引入外部工具:原文说 *"the LLM can help you vibe-code a naive search script as the need arises"* —— 让 LLM 现搓一个朴素搜索脚本(grep 加个粗排序)往往就够用

## 🔄 schema 演化

> Karpathy 原文:*"You and the LLM **co-evolve this over time** as you figure out what works for your domain."*

本文件允许并鼓励演化 —— 某条约定在实践中稳定下来、某条规则反复卡壳或从没被用上时,LLM 应**主动提议**改本文件。流程一步都不能省:**提议**(改哪一条、为什么、改完什么变化)→ **等用户明确同意**(未经确认不得擅自改写 schema)→ **只改被确认的部分**,不顺手重写别处 → 在 `wiki/log.md` 追加一条 `## [YYYY-MM-DD] wiki | schema 更新:<改了什么、为什么>`。
